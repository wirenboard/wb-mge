# WB-MGE v3 — ручной smoke-тест UI

Высокоуровневая визуальная проверка веб-интерфейса шлюза. Эти тесты **не** проверяют функциональность шлюза (Modbus-трафик, корректность кэша, реальные сетевые подключения и т.п.) — они подтверждают, что веб-интерфейс не сломан совсем: все страницы открываются, все кнопки реагируют, формы принимают ввод, ничего не выкидывает в белый экран.

## Цель

Поймать регрессии уровня «нажимаем кнопку — ничего не происходит», «открываешь страницу — пустота», «верстка разъехалась», «модалка не закрывается», «бургер-меню не открывается».

Если какой-то шаг ниже даёт результат, не описанный в «Ожидание», — это баг.

## Что отражать в итоговом отчёте

В отчёт пишем **не только полные поломки**, но и «мягкие» дефекты, которые портят UX:

- **Несинхронное обновление UI** — поля сайдбара/шапки/счётчиков, которые отстают от изменения настройки на 1+ секунду или обновляются только после ручной перезагрузки страницы. Пример: после выключения CACHING тогглера в Register map карточка RS-485 на Dashboard продолжает показывать в строке «Кэш» значение «Включён» ещё несколько секунд (хотя кэш-оверлей уже выключен); или после Stop в Sniffer статус порта в сайдбаре/на карточке обновляется не сразу.
- **Медленные реакции** — кнопки/тогглеры, которые отрабатывают визуально, но фактические данные подтягиваются с заметной задержкой без индикатора загрузки.
- **Неконсистентная валидация** — поле подсвечено как невалидное, но кнопка Save остаётся активной (или наоборот).
- **Расхождения локализации** — пропавшая переменная вроде `"minute"` без числа, частично непереведённые надписи, plurals-ошибки.
- **Отличия мобильного и десктопного состояния одного и того же действия** (например, попап на десктопе открывается справа, на мобиле — снизу, и при этом перекрывает кнопку, которую нажали).
- **Confirm-диалоги для разрушительных действий** — если для одного действия (Factory reset) confirm есть, а для другого (Reboot device) нет, это регрессия, а не «фича».

Формат записи: краткое описание, шаги воспроизведения, ожидаемое vs фактическое, прошивка (видно на Dashboard / System), скриншот при возможности.

## Подготовка

1. Тестовое устройство WB-MGE v.3 включено и доступно по IP в той же сети.
2. Логин по умолчанию `admin` / `admin`.
3. Браузер — последний Chrome / Firefox / Safari. Кэш чистый (Ctrl+Shift+R или приватное окно).
4. Тесты выполнять последовательно по разделам. Если шаг ломает состояние устройства — продолжать со следующего раздела, не перезагружая.
5. В конце всего прогона — пройти раздел «Мобильное разрешение» (это обязательное требование).

## 1. Страница входа

### 1.1. Открытие

1. Открыть в адресной строке `http://<IP>/`.
2. Должно произойти редирект на `#/login`.

**Ожидание:** загружается экран входа: слева — логотип, заголовок «MGE: Your Swiss Army Knife for Modbus», поля **Username** и **Password**, кнопка **Login** (неактивна), ссылка **Documentation**, выпадашка языка, ссылка `wirenboard.com`. Справа — пустая зелёная декоративная панель. Чип `WB-MGE v3 · <hostname>` под логотипом.

### 1.2. Переключение языка

1. Кликнуть в выпадашку языка внизу формы.
2. Выбрать **Русский**.

**Ожидание:** все надписи (заголовок, описание, кнопка, лейблы) переключаются на русский. Кнопка становится «Войти».

3. Поочерёдно проверить **Қазақша**, **Italiano**, **Deutsch**, потом вернуться в English/Русский.

**Ожидание:** для каждого языка надписи меняются, выпадашка не «зависает», страница не моргает.

### 1.3. Активация кнопки

1. Очистить поле логина.
2. Кнопка **Войти** должна быть disabled.
3. Ввести любой текст в логин и в пароль.

**Ожидание:** кнопка становится активной.

### 1.4. Невалидный логин

1. Логин `wrong`, пароль `wrong` → нажать **Войти**.

**Ожидание:** появляется алерт «Введены неверные логин или пароль». Поля остаются заполненными, кнопка снова активна.

### 1.5. Валидный логин

1. Логин `admin`, пароль `admin` → **Войти**.

**Ожидание:** редирект на `#/`, открывается Dashboard, в левой панели снизу появляется кнопка «Выйти».

### 1.6. Ссылка Documentation

1. На странице логина кликнуть **Documentation**.

**Ожидание:** новая вкладка с wiki Wirenboard.

### 1.7. Прямой доступ к защищённому URL без сессии

1. В инкогнито-окне открыть напрямую `http://<IP>/#/sniffer` (без предварительного логина).

**Ожидание:** автоматический редирект на `#/login`. После успешного входа — редирект на `#/sniffer` (исходный маршрут сохраняется, а не заменяется на `#/`).

## 2. Сайдбар (общая навигация)

Этот раздел проверяется один раз — на любой странице после логина (например, на Dashboard).

### 2.1. Состав меню

**Ожидание:** в сайдбаре сверху вниз:
- Логотип Wiren Board (кликабельный, ведёт на `/`).
- Hostname (например, `WB-MGE-30D7CF`).
- Группа **OVERVIEW** → Dashboard.
- Группа **MODBUS TOOLS** → TCP gateway, Sniffer, Repeater, Register map.
- Группа **CONFIGURATION** → Network, Serial ports, System.
- Блок **Port 1** / **Port 2** с статусом IDLE/ACTIVE, текущим режимом и параметрами линии (например, `9600 · 8N2`).
- Ссылки Documentation, Support, Buy devices.
- Кнопка **Logout** снизу.

### 2.2. Активный пункт меню

1. Кликнуть **Sniffer** в меню.

**Ожидание:** строка Sniffer подсвечена зелёной полоской слева, иконка зелёная, страница переключается на сниффер. Адресная строка содержит `#/sniffer`.

### 2.3. Все пункты меню открываются

Поочерёдно кликнуть каждый пункт меню и проверить, что соответствующая страница открывается, заголовок страницы соответствует пункту меню, нет белого экрана / падения JS.

| TCP gateway | TCP gateway / TCP-шлюз |

| Repeater | Repeater / Повторитель |
| Register map | Register map / Карта регистров |
| Network | Network / Сеть |
| Serial ports | Serial ports / Последовательные порты |
| System | System / Система |

### 2.4. Внешние ссылки

1. Кликнуть **Documentation** в сайдбаре — открывается новая вкладка с wiki.
2. **Support** — открывается mailto: или ссылка на сайт поддержки.
3. **Buy devices** — открывается `wirenboard.com`.

### 2.5. Кнопка Logout

1. Кликнуть **Logout**.

**Ожидание:** редирект на `#/login`. Если затем перейти на любой защищённый маршрут (например, `#/sniffer`) — снова редирект на логин. Затем войти обратно для продолжения тестов.

### 2.6. Индикация TX Disabled в сайдбаре

*Предусловие:* в Serial ports → Port N → включить **Disable transmission (TX)** и сохранить настройки.

**Ожидание:** в блоке **Port N** в строке «Line» сайдбара рядом с параметрами линии (например, `9600 · 8N1`) появляется «· ~~TX~~» — зачёркнутое красным цветом «TX».

*После проверки вернуть Disable TX в исходное положение и сохранить.*

## 3. Dashboard

### 3.1. Открытие

1. Перейти на `#/`.

**Ожидание:** заголовок «Dashboard» + крошки «Gateway overview». Две колонки карточек:
- Левая: **Ethernet**, **Wi-Fi**, **Gateway**.
- Правая: **RS-485 · Port 1**, **RS-485 · Port 2**.

Все карточки заполнены данными (IP, MAC, версия прошивки, напряжение питания, uptime, режим/параметры RS-485). В пустых значениях вместо `null` стоит `—`.

### 3.2. Бейджи статусов

В шапке каждой карточки видны разноцветные «таблетки»:
- Ethernet: `Connected` (зелёная) или `Not connected` (серая).
- Wi-Fi: `Enabled` / `Disabled`.
- RS-485: `Active` / `Inactive`.

**Ожидание:** цвета и текст соответствуют статусу.

### 3.3. Кнопки-шестерёнки → переход в настройки

1. Кликнуть шестерёнку в шапке карточки **Ethernet** — переход на `#/network`.
2. Вернуться. Кликнуть шестерёнку в **Wi-Fi** — также `#/network`.
3. Шестерёнка **RS-485 · Port 1** — переход на `#/settings`.
4. Шестерёнка **RS-485 · Port 2** — переход на `#/settings`.

**Ожидание:** каждая шестерёнка работает и ведёт в нужный раздел.

### 3.4. Версия прошивки

1. Найти карточку **Gateway** → строка «Firmware».

**Ожидание:** показана текущая версия. Если у браузера есть доступ в интернет — справа подпись `(up to date)`, когда версия канала совпадает с установленной, или `(in stable: X.Y.Z)` плюс кнопка **Update**, когда в канале другая версия. Если интернета нет — `(update check unavailable)`, без падений.

### 3.5. Кнопка Update (если есть)

1. Если рядом с версией есть кнопка **Update** — кликнуть её.

**Ожидание:** редирект на `#/system`.

### 3.6. Карточка Wi-Fi — режим STA (клиент)

*Выполнять, если устройство подключено к Wi-Fi в режиме клиента.*

**Ожидание:** в карточке **Wi-Fi** отображаются строки:
- **Connection**: «Connected» или «Not connected».
- **SSID**: имя сети (если подключено).
- **IP address**, **MAC address**.
- **RSSI** в dBm (если подключено).

Значения не пустые и не `null`.

### 3.7. Карточка Wi-Fi — режим AP (точка доступа)

*Выполнять, если устройство работает как точка доступа.*

**Ожидание:** в карточке **Wi-Fi** отображаются строки:
- **Number of connections** (количество подключённых клиентов).
- **IP address** (адрес AP), **MAC address** (MAC AP).

RSSI и SSID подключения не отображаются.

## 4. TCP-шлюз

### 4.1. Открытие

1. Перейти в **TCP gateway**.

**Ожидание:** заголовок «TCP gateway», две карточки: «RS-485 · Port 1» и «RS-485 · Port 2». В каждой — селект **Mode**, селект **Bridge mode**, поле **Port** (number input). Кнопка **Save** — disabled.

### 4.2. Переключение режима Modbus

1. В карточке Port 1 переключить **Mode** → `Modbus TCP`.

**Ожидание:** поле **Bridge mode** исчезает (оно нужно только для transparent bridge). Кнопка **Save** становится активной.

2. Переключить обратно → `Transparent bridge`.

**Ожидание:** поле **Bridge mode** появляется снова.

### 4.3. Переключение Bridge mode (Server/Client)

1. **Bridge mode** → `Client`.

**Ожидание:** появляется дополнительное поле **IP address** для адреса удалённого сервера. Кнопка **Save** — активна.

2. **Bridge mode** → `Server`.

**Ожидание:** поле **IP address** исчезает.

### 4.4. Поле Port (числовое поле)

1. Ввести в **Port** значение `0` или `100000` — за пределами диапазона 1–65535.

**Ожидание:** поле подсвечивает невалидность (нативная подсказка браузера или красная рамка), кнопка **Save** не позволяет сохранить.

2. Установить порту Port 1 такое же значение, как у Port 2 (по умолчанию 502 и 503).

**Ожидание:** обе карточки показывают красную подсказку «Port values must be unique» / «Значение порта должно быть уникальным», обе **Save** disabled.

3. Вернуть уникальные значения — подсказка исчезает.

### 4.5. Save (не нажимать, если устройство в проде)

> ⚠️ Сохранение реально меняет конфигурацию шлюза. На тестовом стенде безопасно — нажать **Save** в Port 1 после любого валидного изменения.

**Ожидание:** кнопка показывает состояние загрузки и становится disabled. Через ~1 с — успех, кнопка снова disabled (изменений нет). Перезагрузка страницы возвращает то же значение (изменение применилось).

## 5. Сниффер

### 5.1. Открытие

1. Перейти в **Sniffer**.

**Ожидание:** заголовок «Sniffer». В тулбаре:
- Счётчики `0 packets`, `0 errors`.
- Кнопки выбора порта: **Port 1**, **Port 2** (Port 1 — активна по умолчанию).
- Кнопка **Start** (зелёная).
- Кнопка **▶ Send packet** (outline).
- Кнопка **Clear** (outline).
- Кнопка **Export CSV** (disabled, пока пакетов 0).

Слева — фасетный рейл со **Slave ID** и **Function code** (оба «0 seen · all selected»). Справа — пустая таблица с колонками `# / Time / Δt / Sender / Slave / Function / Payload / Bytes / CRC`.

### 5.2. Переключение порта

1. Кликнуть **Port 2** в тулбаре.

**Ожидание:** Port 2 становится активным (визуально), Port 1 — неактивным. Никакой ошибки.

2. Вернуться на Port 1.

### 5.3. Start / Stop

1. Нажать **Start**.

**Ожидание:** кнопка моментально становится красной **Stop**. Если по шине идёт реальный Modbus-трафик — в таблице появляются строки, иначе остаётся пустой (это допустимо для смоук-теста). Никакого зависания UI.

2. Нажать **Stop**.

**Ожидание:** кнопка возвращается в **Start** (зелёная). Захват прекращается.

### 5.4. Двойной клик Start

1. Кликнуть **Start** дважды подряд (быстро).

**Ожидание:** UI не виснет, кнопка корректно отрабатывает: один клик — Start, второй — Stop. (Подробнее этот и смежные сценарии описаны в разделе [«Sniffer после цикла кэша»](#15-sniffer-после-цикла-кэша) этого документа.)

### 5.5. Clear

1. Если в таблице есть строки — нажать **Clear**.

**Ожидание:** таблица очищается, счётчики становятся `0 packets`. Фасеты также сбрасываются.

### 5.6. Export CSV

1. Если в таблице есть строки — нажать **Export CSV**.

**Ожидание:** браузер скачивает файл `sniffer_port<N>.csv`. Если пакетов нет — кнопка disabled.

### 5.7. Попап отправки пакета

1. Нажать **▶ Send packet**.

**Ожидание:** открывается всплывающее окно с формой: Slave ID, Function code, Start address, Value/Quantity, сегментный переключатель **Read / Write**. Видно превью кадра в HEX.

2. Изменить любое поле — превью обновляется.

3. Переключить сегментный контрол с **Read** на **Write**.

**Ожидание:** список Function code меняется (FC01–FC04 → FC05/FC06/FC15/FC16), лейбл четвёртого поля меняется с «Count» на «Value», превью кадра обновляется.

4. В режиме **Read** ввести в поле **Count** значение `25` и переключить Function code с **FC03** на **FC04**.

**Ожидание:** введённое значение `25` сохраняется — поле не сбрасывается на `10`, превью обновляется под новый FC. Значение заменяется только тогда, когда новый FC его не принимает: в режиме **Write** значение `300` при переключении на **FC05** (coil принимает только 0 или 1) заменяется на `1`.

5. Ввести заведомо некорректный Slave ID (`0` или `256`).

**Ожидание:** превью кадра показывает `—`, кнопка отправки disabled.

6. Закрыть попап (крестик или клик вне попапа).

**Ожидание:** попап исчезает без ошибок.

7. Не останавливая захват (кнопка **Stop** не нажата), открыть попап **▶ Send packet** снова.

**Ожидание:** попап открывается поверх таблицы. Захват продолжается (строки добавляются в таблицу за попапом). Нет визуального сбоя, нет закрытия попапа при поступлении нового пакета.

Если по выбранному порту в настройках включён **Disable TX** — кнопка **Send packet** должна быть **disabled**.

#### Автозапуск захвата при отправке

> Шаги ниже реально отправляют кадр в шину — выполнять только на стенде. Проверяется подсказка под кнопкой отправки: она обязана описывать то, что произошло на самом деле.

1. Остановить захват (**Stop**), открыть **▶ Send packet** и нажать кнопку отправки.

**Ожидание:** захват запускается сам (кнопка в тулбаре становится красной **Stop**), кадр уходит уже после того, как захват заработал, и под кнопкой отправки вместо подсказки про CRC появляется «Перехват запущен автоматически, чтобы пакеты попали в список». Отправленный кадр (и ответ, если он есть) видны в таблице.

2. Не останавливая захват, нажать отправку ещё раз.

**Ожидание:** кадр уходит сразу, подсказка под кнопкой обычная («CRC добавляется автоматически») — ничего не заявляет о запуске захвата.

3. (Если получится поймать момент.) Остановить захват, нажать отправку и сразу же нажать **Stop** в тулбаре, пока кадр ждёт подключения сокета.

**Ожидание:** кадр всё равно уходит — сразу, не дожидаясь пятисекундного таймаута, — а подсказка становится третьей, отличной от двух предыдущих: «Отправлено без активного перехвата, пакеты не попадут в список». Подсказка про автозапуск в этом случае появляться не должна. Та же подсказка ожидается, если сокет захвата так и не открылся: отправка не зависает и не отменяется (кадр уходит примерно через 5 с), просто пакеты не попадут в таблицу.

### 5.8. Фасеты Slave ID / Function code

Эти контролы видны, только если есть пакеты. Если пакеты есть:

1. Кликнуть на строку в Slave ID.

**Ожидание:** строка отмечается галкой, в таблице видны только пакеты этого слейва. Счётчик в шапке фасета меняется на `N selected`.

2. Кликнуть **clear** в шапке фасета — фильтр сбрасывается.

Аналогично для **Function code**.

### 5.9. Декодер пакета

1. Кликнуть на любую строку в таблице (если есть пакеты).

**Ожидание:** строка подсвечивается, ниже / справа появляется панель с разбором байтов (адрес, функция, payload, CRC).

### 5.10. Счётчик ошибок CRC

*Выполнять только при наличии трафика с повреждёнными пакетами на шине.*

**Ожидание:** счётчик `N errors` в тулбаре увеличивается при поступлении пакетов с неверным CRC. После нажатия **Clear** — сбрасывается в `0 errors`.

## 6. Повторитель

Прозрачный RS-485 serial↔serial ретранслятор: режим порта `repeater` побайтно пересылает данные между Port 1 и Port 2 в обе стороны (удлинение линии / восстановление целостности сигнала). Включение/выключение — одним тогглом, который выставляет **оба** порта в режим `repeater` (или обратно в `disabled`).

### 6.1. Открытие

1. Перейти в **Repeater** (группа Modbus tools, между Sniffer и Register map).

**Ожидание:** заголовок «Repeater» / «Повторитель», крошки про прозрачную передачу RS-485 между Port 1 и Port 2. Сверху — жёлтый баннер **Warning / Внимание** с предупреждением, что при активном повторителе оба сегмента RS-485 ведут себя как электрически соединённые, и при наличии мастеров с обеих сторон шины столкнутся. Ниже — карточка **Bridge / Мост** (подпись «Port 1 ↔ Port 2») в три колонки: панель **Port 1** слева, центр с большим тогглом и стрелками потока, панель **Port 2** справа. В каждой панели порта — шапка «RS-485» с параметрами линии (например, `9600 · 8N1`), заголовок порта и счётчик **Dropped bytes / Потеряно байт** (красным).

### 6.2. Состояние «выключено»

*Предусловие: оба порта НЕ в режиме repeater (например, после сброса / в `disabled`).*

**Ожидание:** большой тоггл в центре показывает **Disabled / Отключён** и подпись-хинт **Click to enable / Нажмите, чтобы включить**. Блок с Uptime/Avg скрыт (он появляется только во включённом состоянии).

### 6.3. Включение повторителя

1. Нажать большой тоггл (**Click to enable**).

**Ожидание:** тоггл оптимистично переключается в **Enabled / Включён**, под ним появляются строки **Uptime / Время работы** (формат `ЧЧ:ММ:СС`) и **Avg / Средн.** (средний поток, B/s). Запрос выставляет режим `repeater` обоим портам (POST `/ports/1/mode` и `/ports/2/mode` с `{"mode":"repeater"}`). В сайдбаре у **обоих** портов строка «Режим» становится **Repeater / Повторитель**. Пока запрос «в полёте» — тоггл disabled (повторные клики не проходят).

2. Если по шине идёт трафик — понаблюдать за стрелками потока.

**Ожидание:** счётчики пересланных байт растут: стрелка вправо (Port 1 → Port 2) и влево (Port 2 → Port 1) показывают значения в байтах (крупные числа сгруппированы тонким пробелом, например `18 472`), Avg пересчитывается. Реальный трафик для smoke не обязателен — нулевые значения допустимы.

### 6.4. Выключение повторителя

1. Нажать тоггл ещё раз (**Click to disable / Нажмите, чтобы отключить**).

**Ожидание:** тоггл возвращается в **Disabled / Отключён**, блок Uptime/Avg скрывается. Запрос выставляет обоим портам `{"mode":"disabled"}`; в сайдбаре «Режим» у обоих портов становится **Disabled / Отключён**.

### 6.5. Ошибка переключения

*Выполнять при возможности оборвать связь: DevTools → Network → Offline на момент клика.*

1. Перевести вкладку в Offline и нажать тоггл.

**Ожидание:** запрос не проходит, тоггл откатывается в исходное состояние (оптимистичное переключение отменяется), появляется алерт о потере связи. UI не виснет.

### 6.6. Локализация

1. Переключить язык интерфейса.

**Ожидание:** заголовок, крошки, баннер, подписи тоггла (Enabled/Disabled, Click to enable/disable), Uptime/Avg, Dropped bytes — переведены. Пункт **Repeater** в сайдбаре также меняет название (например, «Повторитель» на русском).

## 7. Карта регистров

### 7.1. Открытие при выключенном кэше

1. Перейти в **Register map** (после сброса устройства или если кэш не включался).

**Ожидание:** заголовок «Register map». В шапке тогглер `CACHING OFF`. В теле — большая плашка с иконкой сетки, текстом «Register map caching is disabled» и кнопкой **Enable caching**. В правой панели Settings видны кнопки портов: **Port 1** должна быть **активна** (подсвечена), **Port 2** — неактивна. Это состояние по умолчанию — порт 1 предвыбран даже до включения кэша. Если обе иконки неактивны — это регрессия.

### 7.2. Включение кэша через кнопку

1. Нажать **Enable caching**.

**Ожидание:** тогглер переключается в `CACHING ON`. Большая плашка исчезает, появляется спиннер «Loading…» и затем таблица устройств. Кэш — это независимый оверлей поверх транспортного режима порта; включение кэша на порту, который был `Отключён`, открывает его как `Пассивный (прослушка)`, поэтому в сайдбаре у выбранного порта строка «Режим» становится **«Пассивный (прослушка)»** (если порт уже был в `TCP-мост` или `Пассивный (прослушка)`, режим не меняется). Сам факт включённого кэша сайдбар **не** показывает — он виден отдельной строкой «Кэш: Включён» в карточке RS-485 этого порта на Dashboard.

### 7.3. Выключение кэша через тогглер

1. Кликнуть тогглер `CACHING ON` в шапке.

**Ожидание:** возвращается состояние «Caching disabled». Выключение кэша снимает только оверлей (POST `cache enabled:false`) и **не** трогает транспортный режим порта — поэтому в сайдбаре строка «Режим» остаётся **«Пассивный (прослушка)»** (порт не возвращается в `Отключён`). На Dashboard в карточке RS-485 строка «Кэш» переключается в «Выключен».

### 7.4. Панель Settings (когда кэш включён)

При включённом кэше в правой части страницы видна панель с настройками:
- Радиокнопки **Port 1** / **Port 2** (выбор активного порта-источника).
- Поле **TCP server port** (порт Modbus TCP-сервера, по умолчанию 504).
- Тогглер включения TCP-сервера.
- Поле **Value timeout (s)** — под ним подсказка «Максимум 65535 с (≈18 ч)».
- Кнопка **Save**.

1. Переключить радио с Port 1 на Port 2.

**Ожидание:** радио переключается, кнопка **Save** активна.

2. Нажать **Save**.

**Ожидание:** надпись «Saving…», затем «Saved» (зелёная) → через 3 с скрывается. Кэш-оверлей реально переезжает на выбранный порт: на Port 1 он снимается (транспортный режим Port 1 при этом не трогается), а Port 2 открывается как `Пассивный (прослушка)` с активным кэшем. Перемещение оверлея видно по строке «Кэш» в карточках RS-485 на Dashboard (у Port 1 — «Выключен», у Port 2 — «Включён»).

3. Не уходя со страницы, переключить радио обратно с Port 2 на **Port 1** и **в том же заходе** изменить остальные поля панели: вписать другой **TCP server port** (например, 505), переключить тогглер TCP-сервера и вписать другой **Value timeout (s)** (например, 90). Нажать **Save** один раз.

**Ожидание:** обратное направление (2 → 1) работает так же, как прямое: «Saving…» → «Saved», кэш-оверлей переезжает обратно на Port 1 (в карточках RS-485 на Dashboard у Port 1 — «Кэш: Включён», у Port 2 — «Выключен»), транспортный режим Port 2 при этом не трогается. Ошибки/красной надписи быть не должно.

**Это главная проверка данного раздела.** Раньше прошивка отвечала на такой запрос 409 Conflict («оверлей уже занят другим портом»), и один этот отказ ронял весь Save: порт-источник не переезжал **и** остальные поля того же сохранения не доезжали до устройства. Поэтому обязательно проверить, что применились именно **все** поля: **TCP server port**, тогглер TCP-сервера и **Value timeout (s)**.

4. Обновить страницу (F5).

**Ожидание:** после перезагрузки панель Settings показывает выставленные в шаге 3 значения (Port 1, новый TCP server port, новое состояние тогглера, новый Value timeout) — значит, они действительно сохранены на устройстве, а не только в UI.

### 7.7. Переключение активного порта-источника и перезагрузка таблицы

*Выполнять при наличии устройств в кэше хотя бы на одном из портов.*

1. При включённом кэше на Port 1 переключить радио на **Port 2** и нажать **Save**.

**Ожидание:** кэш-оверлей переезжает с Port 1 на Port 2. В сайдбаре строка «Режим» у Port 1 остаётся транспортным значением (кэш с него только снят, транспорт не трогается — обычно `Пассивный (прослушка)`), а Port 2 открывается как `Пассивный (прослушка)`. То, что кэш теперь на Port 2, отражает строка «Кэш» в карточках RS-485 на Dashboard (у Port 2 — «Включён», у Port 1 — «Выключен»). Таблица устройств перезагружается и отражает данные Port 2 (или пустое состояние, если на Port 2 нет устройств). Нет зависания, нет белого экрана.

2. Теперь обратное направление: переключить радио с **Port 2** на **Port 1** и нажать **Save**.

**Ожидание:** ровно то же самое, зеркально — оверлей переезжает с Port 2 на Port 1 (в карточках RS-485 у Port 1 «Кэш: Включён», у Port 2 «Выключен»), транспортный режим Port 2 не трогается, таблица перезагружается под данные Port 1. Ошибки быть не должно.

Направление 2 → 1 проверять обязательно: прошивка применяет пару переключений в фиксированном порядке (сначала Port 1, потом Port 2), поэтому раньше именно это направление упиралось в 409 Conflict, тогда как 1 → 2 проходило. Симптом был асимметричным — кэш «переезжал только в одну сторону».

3. Проверить, что кэш действительно собирается с нового порта: подождать несколько секунд опроса и убедиться, что в таблице появляются устройства Port 1 (значения обновляются, «возраст» значений сбрасывается). Накопленные ранее данные Port 2 при переезде отбрасываются — это ожидаемо, пул кэша один и он не различает порты.

### 7.5. Поиск, expand/collapse

При наличии устройств в таблице:

1. Ввести в строку поиска `1` или часть hex-адреса.

**Ожидание:** таблица фильтруется. Если совпадений нет — пустое состояние без падений.

2. Нажать **Expand all** / **Collapse all** (если такие кнопки есть в шапке таблицы).

**Ожидание:** все строки раскрываются / сворачиваются.

### 7.6. Export

1. Нажать **Export JSON** (или кнопку загрузки JSON).

**Ожидание:** браузер скачивает `register-map-<timestamp>.json`. Файл — валидный JSON.

### 7.8. Кламп Value timeout к максимуму прошивки

Прошивка принимает таймаут значения только в диапазоне 0–65535 с (0 = таймаут отключён; 65535 с ≈ 18 ч — максимум uint16). UI клампит введённое значение перед сохранением, иначе прошивка молча отбросит выход за диапазон.

*Выполнять при включённом кэше (виден блок Settings).*

1. В поле **Value timeout (s)** ввести значение больше максимума (например, `99999`) и нажать **Save**.

**Ожидание:** после сохранения поле показывает уже зажатое значение `65535` (UI отражает кламп обратно в инпут), статус меняется на «Saved». Нативный спиннер числового поля тоже не даёт выйти за `max=65535`.

2. Полностью очистить поле **Value timeout (s)** и нажать **Save**.

**Ожидание:** пустое (нечисловое) значение трактуется как `0` — поле показывает `0` (таймаут отключён), без падений и без `NaN`.

### 7.9. Попап «Карта регистров устройства» (ссылка в крошках)

Под заголовком «Register map» в строке-крошках есть кликабельная ссылка-хвост: «… cleared on reset · **info registers available**» (рус. «… сбрасывается при перезагрузке · **доступны регистры информации**»). Ссылка видна **всегда**, независимо от состояния кэша.

1. Кликнуть ссылку **info registers available** / **доступны регистры информации** в крошках.

**Ожидание:** открывается модальный попап с затемнённым фоном и заголовком «Device register map» / «Карта регистров устройства», рядом — техническая подпись `Unit ID 255 (0xFF)`. В теле: вводный абзац, таблица **Input registers (FC04, read-only)** (колонки Address (dec) / Address (hex) / Regs / Type / Description), таблица **Holding registers (FC03, read-only)** и блок **Notes / Примечания**. Тело прокручивается, попап не «вылазит» за экран.

2. Закрыть попап тремя способами поочерёдно (каждый раз открывая заново): крестик ✕ в шапке, клик по затемнённому фону вне карточки, клавиша **Esc**.

**Ожидание:** во всех трёх случаях попап закрывается без ошибок, затемнение убирается, страница Register map снова интерактивна.

3. Переключить язык интерфейса (например, на English) и снова открыть попап.

**Ожидание:** надписи интерфейса попапа (заголовок, названия секций, заголовки колонок, кнопка закрытия) переведены. Технические описания регистров и примечания показываются на en/ru (для остальных языков — английский фолбэк) — это ожидаемо, не баг.

## 8. Сеть

### 8.1. Открытие

1. Перейти в **Network**.

**Ожидание:** заголовок «Network». Две карточки: **Ethernet** и **Wi-Fi**. Обе **Save** — disabled.

### 8.2. Ethernet — DHCP

1. Снять чекбокс **DHCP client** (тогглер).

**Ожидание:** появляются три поля: **IP**, **Gateway**, **Mask**. Кнопка **Save** активна.

2. Ввести в IP невалидное значение (например, `999.999.999.999`).

**Ожидание:** поле подсвечивает невалидность.

3. Включить **DHCP client** обратно.

**Ожидание:** поля исчезают. Save снова disabled (если других изменений нет).

### 8.3. Wi-Fi — режим

1. В выпадашке **Mode** переключить на **Disabled**.

**Ожидание:** все поля Wi-Fi скрываются. Save активна.

2. Переключить на **Client (sta)**.

**Ожидание:** появляются поля для подключения к сети (SSID-селект, защита, пароль, DHCP-клиент, опционально статический IP).

3. Кликнуть селект SSID (с иконкой Reload).

**Ожидание:** запускается сканирование, появляются доступные сети. Не падает, даже если сетей нет.

4. Кликнуть Reload-иконку рядом — повторное сканирование.

5. Ввести вручную SSID, которого нет в списке.

**Ожидание:** имя добавляется в список и выбирается.

6. Переключить **Mode** обратно на **Access Point (ap)**.

**Ожидание:** поля для AP: SSID, защита (Open/WPA2/WPA3), пароль, статический IP, маска, шлюз.

7. В защите выбрать **Open** — поле пароля скрывается. Выбрать WPA2 — поле возвращается с placeholder.

8. Ввести SSID длиннее 32 символов или с не-ASCII символами.

**Ожидание:** валидация показывает подсказку, Save запрещает сохранение.

> ⚠️ Кнопка Save в этой форме может оставаться визуально активной при невалидных значениях (валидация на сабмите). Чтобы проверить, что недопустимое значение реально не сохраняется, **обязательно нажать Save** и убедиться, что появляется ошибка/тост или поле подсвечивается красным, а конфиг на устройстве не меняется (перезагрузить страницу и посмотреть, что значение откатилось к старому). 

9. Установить защиту **WPA2**, ввести пароль, затем переключить на **Open** и обратно на **WPA2**.

**Ожидание:** при возврате на WPA2 поле пароля пустое (или заполнено прежним значением). Поле не содержит мусора, кнопка **Save** активна.

Если в прошивке `wifi_perm_disable=true` — карточки Wi-Fi не должно быть вовсе, только Ethernet.

## 9. Последовательные порты

### 9.1. Открытие

1. Перейти в **Serial ports**.

**Ожидание:** заголовок «Serial ports». Две карточки RS-485 (Port 1, Port 2) + карточка **I/O Bus** под Port 2. Все Save disabled.

### 9.2. RS-485 — параметры линии

В каждой карточке проверить, что доступны:
- **Baud rate**: 1200 / 2400 / 4800 / 9600 / 19200 / 38400 / 57600 / 115200.
- **Parity**: None / Even / Odd.
- **Stop bits**: 1 / 1.5 / 2.
- **Data bits**: 5 / 6 / 7 / 8.
- Чекбоксы: **Failsafe bias**, **120Ω termination resistor**, **Disable transmission (TX)**.

1. Сменить baud rate в Port 1 — Save активна.
2. Вернуть исходное значение — Save снова disabled.

**Ожидание:** компонент корректно определяет «изменилось / не изменилось».

3. Под тогглерами **Failsafe bias** и **120Ω termination resistor** проверить наличие поясняющего текста-подсказки (серый, мелкий шрифт).

**Ожидание:** под **Failsafe bias** — подсказка про резисторы смещения 560 Ω (включать, когда модуль работает мастером); под **120Ω termination resistor** — подсказка про резистор-терминатор 120 Ω (включать, когда модуль в конце шины), причём её текст разбит на две строки (есть намеренный перенос). У тогглера **Disable transmission (TX)** подсказки нет — при его включении ниже появляется отдельное жёлтое предупреждение (⚠). При переключении языка интерфейса подсказки переводятся вместе с остальными надписями.

### 9.3. I/O Bus

1. Переключить тогглер **Enable I/O Bus**.

**Ожидание:** Save активна. Сохранение работает.

### 9.4. I/O Bus и Disable TX на Port 2

1. При включённом **I/O Bus** включить также **Disable transmission (TX)** на Port 2 и нажать **Save**.

**Ожидание:** интерфейс не блокируется, сохранение обоих параметров выполняется без ошибки. (Это smoke-тест: реальная работа шины не проверяется.)

### 9.5. Независимое сохранение карточек

Этот сценарий проверяет, что разные блоки настроек на одной странице ведут себя как независимые формы — сохранение одной не сбрасывает «грязные» изменения в другой.

1. На Port 1 изменить, например, **Baud rate** (но не нажимать Save) — Save Port 1 активна.
2. На Port 2 изменить, например, **Parity** (но не нажимать Save) — Save Port 2 активна.
3. Нажать **Save** на Port 1.

**Ожидание:** сохранение применяется только к Port 1. Изменённое, но не сохранённое значение **Parity** на Port 2 **остаётся в поле**, Save Port 2 продолжает быть активной. Никакого «отката» Port 2 к серверному значению не происходит.

1. Нажать **Save** на Port 2.

### 10.6. Firmware

**Ожидание:** в карточке видны строки **Update channel** (выпадашка `Stable`/`Testing`), **Channels**, **Current version**, **Install from file**, **Reboot**.

#### 10.6.1. Канал обновлений

1. Открыть выпадашку **Update channel** и переключить `Stable` → `Testing`.

**Ожидание:** значение сохраняется сразу, без отдельной кнопки Save (тост «data updated»). Строка **Channels** остаётся прежней, но выделенным (жирным) становится `testing`, а предложение в строке **Current version** пересчитывается на версию канала testing. Страница не перезагружается. В сетевой вкладке — только `POST /settings`, повторной загрузки `release-versions.yaml` **нет**.

2. Вернуть канал обратно на `Stable`.

**Ожидание:** предложение возвращается к версии канала stable.

#### 10.6.2. Строка Channels

**Ожидание:** показаны сразу обе версии в виде `stable: X.Y.Z · testing: X.Y.Z`. Выбранный канал выделен. Рядом с версией, совпадающей с установленной, стоит пометка **installed** (если обе совпали — пометка стоит у обеих). Канал, версию которого не удалось разобрать, показан прочерком `—`; второй канал при этом продолжает работать.

#### 10.6.3. Строка Current version в трёх состояниях

1. **Обычное состояние (есть интернет):** рядом с версией в скобках — `in stable: X.Y.Z`. Если версия канала отличается от установленной, справа есть кнопка **Update to X.Y.Z** (в том числе когда версия канала **ниже** установленной — это ожидаемое поведение).

2. **Нет доступа к fw-releases** (отключить интернет на машине с браузером или заблокировать домен): перезагрузить страницу.

**Ожидание:** в скобках — `update check unavailable`, кнопки **Update to X.Y.Z** нет, но рядом есть кнопка **Check state**: она повторяет проверку, и пока интернета нет — состояние не меняется, а после его возврата предложение появляется без перезагрузки страницы. «Install from file» продолжает работать.

3. **Плата без опубликованных каналов** (проверяется на устройстве, сигнатуры которого нет в манифесте): в скобках — `no update channels published for this board yet`, кнопки **Update to X.Y.Z** нет, кнопка **Check state** есть. Этот текст обязан отличаться от `update check unavailable`.

#### 10.6.4. Обновление одной кнопкой

> ⚠️ Реально меняет прошивку устройства. Выполнять только на стенде.

1. Нажать **Update to X.Y.Z**.

**Ожидание:** браузерный confirm. **Cancel** — ничего не происходит.

2. Подтвердить.

**Ожидание:** в скобках идёт `downloading… N%`, затем `Updating`, затем `the device is rebooting…` и модалка переподключения. Кнопка обновления и выпадашка канала на всё это время заблокированы. Уход на другую страницу и возврат на System **не** прерывает операцию и **не** запускает вторую закачку.

3. Дождаться возвращения устройства.

**Ожидание:** `updated to X.Y.Z`, через ~2 с страница сама перезагружается, в **Current version** — новая версия. Если прошивка не применилась, показывается `the version did not change — the update was not applied` (без автоперезагрузки), а если устройство не вернулось за ~90 с — `the device did not come back online`.

4. Конфликт «обновление уже идёт» (ответ 409). Просто нажать **Update to X.Y.Z** второй раз нельзя: после успешной заливки кнопки в карточке уже нет. Состояние надо получить со второй стороны, пока устройство ещё не перезагрузилось — окно между ответом 200 и перезагрузкой около секунды, так что может понадобиться несколько попыток. Два способа:

   - **Вариант А (вторая вкладка, кнопка обновления).** Заранее открыть веб-интерфейс во второй вкладке на странице System и дождаться в ней предложения **Update to X.Y.Z**. В первой вкладке запустить обновление и, как только там появится `the device is rebooting…`, сразу нажать **Update to X.Y.Z** во второй вкладке.
   - **Вариант Б (вторая вкладка, ручная заливка).** Во второй вкладке заранее выбрать файл прошивки в **Install from file**, но **не** нажимать Update. В первой вкладке запустить обновление по кнопке и, как только там появится `the device is rebooting…`, нажать **Update** под «Install from file» во второй вкладке: файл уже выбран, поэтому `POST /update` уходит сразу, без шага скачивания, и попадает в то же окно между ответом 200 и перезагрузкой. Ручная заливка идёт в тот же эндпоинт `POST /update` и получает тот же отказ. Именно во второй вкладке: в первой этот контрол на фазах скачивания, заливки и перезагрузки заблокирован, нажать его там невозможно.

**Ожидание:** устройство отвечает **409**, и браузер показывает именно сообщение о конфликте: в варианте А в скобках у версии — `An update is already running, the device will reboot shortly` / «Обновление уже идёт, устройство скоро перезагрузится», в варианте Б — такой же текст в тосте. Кнопки обновления в карточке нет, рядом есть **Check state**; нажатие **Check state** после перезагрузки устройства возвращает обычное предложение.

**Обязательно проверить, что сообщение — именно про конфликт, а не общая ошибка обновления** (`Firmware update error` / «Ошибка обновления прошивки») и не `could not download the firmware` / «не удалось скачать прошивку». Это единственный способ убедиться, что ответ 409 доезжает до браузера: прошивка отвечает на такой запрос и сразу закрывает сокет, не дочитывая тело, и если бы ответ терялся по дороге, отказ выглядел бы как обычный сетевой сбой — а пользователь решил бы, что прошивка битая, и полез бы перезаливать.

#### 10.6.5. Установка из файла

1. Кликнуть **Choose file** под «Install from file».

**Ожидание:** открывается диалог выбора файла. (Реально файл не загружать, если нет необходимости.)

### 10.9. Factory reset

2. Изменить **Device name** на произвольное (например, `test-device`) и нажать **Save** в карточке. Убедиться, что изменение применилось (hostname виден в сайдбаре и в ссылке `http://test-device.local`).

> ⚠️ **OK не нажимать** — это уничтожит конфигурацию устройства. В смоук-тесте проверяем только сам факт открытия confirm-диалога.

> Если тест проводится в рамках полного прогона с реальным сбросом: нажать **OK** → дождаться перезагрузки → убедиться, что hostname вернулся к заводскому (вида `WB-MGE-XXXXXX`), а baud rate Port 1 снова равен заводскому значению (9600). Это подтверждает, что Factory reset действительно очищает NVS-настройки, а не просто перезагружает устройство.

## 15. Sniffer после цикла кэша

Один из неочевидных сценариев: запустить сниффер после того, как на порту был включён, а затем выключен кэш. Полезен, потому что задействует взаимодействие двух страниц — **Register map** и **Sniffer**.

Контекст: кэш — это независимый per-port оверлей поверх транспортного режима (`disabled` / `tcp_bridge` / `passive`), а живой сниффер — это оверлей отображения поверх WebSocket. Sniffer.vue **не** переключает порт в какой-то «режим сниффера» (такого режима больше нет). При старте он смотрит текущий транспортный режим порта через `GET /info` и переключает порт в `passive` **только если** порт `disabled` (нужно открыть serial); для `tcp_bridge` и `passive` serial уже открыт, и режим не меняется. Запрос `POST /ports/N/mode {"mode":"sniffer"}` теперь невалиден и вернул бы **400** («Unknown mode value»).

При выключении кэша на странице Register map снимается только оверлей (POST `cache enabled:false`), транспортный режим порта **не** трогается — то есть после цикла кэша порт обычно остаётся в `passive` (serial открыт).

### Шаги

1. Открыть веб-интерфейс.
2. Перейти в **Register map**.
3. Включить кэширование — нажать тогглер. Порт открывается как `passive` с активным кэш-оверлеем.
4. Подождать 2–3 секунды, чтобы кэш стал активным.
5. Выключить кэширование — нажать тогглер ещё раз. Снимается только кэш-оверлей; транспортный режим порта остаётся `passive`.
6. Перейти в **Sniffer**.
7. Выбрать порт 1 (или тот, который использовался для кэша).
8. Нажать **Start**.

**Ожидание:** поскольку порт уже `passive` (serial открыт), Start **не** переключает режим — он сразу открывает WebSocket; в таблице в течение секунды появляются пакеты (если на шине идёт трафик). Если таблица пустая при наличии трафика — это регрессия.

### Как это устроено в коде

`Sniffer.vue:startCapture()` перед подключением WebSocket запрашивает текущий режим порта через `GET /info`. Живой сниффер работает поверх WebSocket и требует лишь открытого serial-порта. Если порт `disabled` — отправляется `POST /ports/N/mode {"mode":"passive"}`, после чего код ждёт 500 мс, пока прошивка переинициализирует UART, и только затем открывает WebSocket. Если порт уже `tcp_bridge` или `passive` — serial уже открыт, режим **не** переключается, WebSocket открывается сразу.

### Смежные кейсы

#### Сценарий 2: Старт при порте в `passive` (baseline — должно работать)

1. **Register map** → включить и выключить кэш (порт остаётся `passive`).
2. Перейти в **Sniffer**, нажать **Start**.
3. **Ожидание:** режим не переключается, данные появляются сразу.

#### Сценарий 3: Старт при активном кэш-оверлее

1. **Register map** → включить кэш (порт открывается как `passive` с активным кэш-оверлеем).
2. Перейти в **Sniffer**, нажать **Start**.
3. **Ожидание:** сниффер работает параллельно с кэшем — оба оверлея аддитивно используют один открытый `passive`-транспорт. Режим **не** переключается.

#### Сценарий 4: Старт при порте в `tcp_bridge`

1. Убедиться, что порт в режиме `tcp_bridge`.
2. Перейти в **Sniffer**, нажать **Start**.
3. **Ожидание:** режим **не** переключается (serial уже открыт под TCP-мост), WebSocket открывается сразу. В таблице в течение секунды появляются пакеты (если на шине идёт трафик). Если таблица пустая при наличии трафика — это регрессия.

#### Сценарий 5: Двойной клик Start

1. Порт в режиме `disabled` (например, сразу после сброса).
2. Быстро кликнуть **Start** дважды.
3. **Ожидание:** создаётся только одно WebSocket-соединение. Кнопка превращается в **Stop** сразу после первого клика, поэтому второй клик трактуется как **Stop**, а не как второй **Start**.

#### Сценарий 6: Клик Stop во время процесса Start

1. Порт в `disabled`.
2. Нажать **Start** (запускается переключение в `passive` + 500 мс задержка).
3. Нажать **Stop** до того, как 500 мс истекут.
4. **Ожидание:** WebSocket НЕ подключается, пакеты не появляются. Кнопка возвращается в **Start**.
