# Защита от копирования

В устройстве реализована защита от несанкционированного копирования.

В основе лежит проверка подписи (кода защиты), хранимой в eFuse block 3, а также проверка перемычек на GPIO микросхемы расширителя портов.

Код формируется из MAC-адреса (зашитого в eFuse на производстве Espressif) устройства и является уникальным для каждого устройства.

## Алгоритм формирования кода защиты

Формирование кода основано на использовании алгоритма шифрования HMAC-SHA-256.

Сначала генерируется 32-байтный хеш из 6-байтного MAC-адреса с использованием 32-байтного ключа.
Далее из 32-байтного хеша формируется 12-байтный код защиты с использованием таблицы перестановок.

## Генерация кода защиты

Ключи (ключ шифрования и таблица перестановок) заданы в файле `keys.txt`.
Файл должен содержать 2 строки с 16-ричными значениями, разделенными пробелами.

В первой строке задается 32-байтный ключ шифрования.
Во второй строке задается таблица перестановок для получения 12-байтного кода (все значения должны быть уникальными и быть в диапазоне от `00` до `1F`).

В файле ключей допускаются пустые строки и комментарии, начинающиеся с символа `#` в начале строки.

Для генерации кода по MAC-адресу используется скрипт `copy_prot_helper.py`.

Пример использования:

``` bash
cd copy_protection
./copy_prot_helper.py --mac 04:83:08:D7:B3:00 --keys keys.txt --out sec_code.bin
```
В результате будет сгенерирован бинарный файл `sec_code.bin` с кодом защиты, размер файла 12 байт.
Данный файл можно использовать для прошивки кода во фьюзы устройства с помощью утилиты `espefuse.py`.

## Хранение ключей в прошивке

В прошивке хранятся:
- ключ шифрования (в перемешанном виде)
- таблица перестановок для кода безопасности (в перемешанном виде)
- таблица перестановок для ключа шифрования
- таблица перестановок для таблицы перестановок кода безопасности

Данные массивы храняется не подряд, а с некоторыми произвольными отступами.

## Генерация заголовочного файла с ключами

При сборке проекта для генерации заголовочного файла с ключами используется этот же скрипт `copy_prot_helper.py`.

На входе скрипт получает те же ключи из файла `keys.txt`, а также таблицы перестановок из файла `swap_tables.txt`.

Файл `swap_tables.txt` должен содержать 2 строки с 16-ричными значениями, разделенными пробелами.

В первой строке содержится таблица перестановок для получения 32-байтного ключа (все значения должны быть уникальными и быть в диапазоне от `00` до `1F`).

Во второй строке содержится таблица перестановок для получения 12-байтной таблицы перестановок кода безопасности (все значения должны быть уникальными и быть в диапазоне от `00` до `0B`).

В файле таблиц перестановок `swap_tables.txt` допускаются пустые строки и комментарии, начинающиеся с символа `#` в начале строки.

Пример использования:

``` bash
cd copy_protection
./copy_prot_helper.py --keys keys.txt --swap_tables swap_tables.txt --out_header ../main/copy_protection/keys.h
```

В результате работы скрипта `copy_prot_helper.py` генерируется заголовочный файл `keys.h`, используемый при сборке проекта.

## Логика проверки валидности устройства

В прошивке реализована следующая логика:
1) В модуле `sys_info.c` считывается код защиты из eFuse и помещается в `sys_info.security_code`. Чтение производится вместе с чтением сигнатуры устройства.
2) Перед инициализацией системы защиты выполняется инициализация ключей: формируются в RAM действительные ключ шифрования и таблица перестановок (функция `copy_protection_init_keys()`)
3) Инициализация системы защиты (функция `copy_protection_init()`):
- Вычисляется хеш от MAC-адреса
- Генерируется случайные времена задержек для задач (см. ниже)
- Выполняется проверка перемычек на GPIO расширителя портов
- Создаются 3 задачи:
  - `sys_monitor_task()`
  - `security_code_task()`
  - `port_expander_task()`
4) Задача `port_expander_task()` ожидает время от `4183` до `7123` мс, а затем:
- Повторно выполняет проверку перемычек на GPIO расширителя портов
- По результату проверки данная задача выставляет соответствующий флаг события (с учетом первой проверки)
- Завершает свое выполнение
5) Задача `security_code_task()` ожидает время от `5312` до `7957` мс, а затем выполняет:
- Формирование 12-байтного эталонного защитного кода
- Сравнение данного кода, хранящегося в `sys_info.security_code`, с эталонным кодом. Для сравнения используется функция `consttime_memeq()` с фиксированным временем работы
- По результату проверки данная задача выставляет соответствующий флаг события
- Завершает свое выполнение
6) Задача `sys_monitor_task()` ожидает время от `9568` до `11231` мс, а затем:
- Проверяет флаги, выставленные задачами `port_expander_task()` и `security_code_task()`
- Если флаги не были выставлены, или выставлен FAIL-флаг хотя бы одной из задач, выполняется блокировка части функционала устройства
- Завершает свое выполнение

Весь процесс занимает итого около 16 секунд (максимальное значение времени) после запуска устройства.

## Блокировка функционала

В случае сработки системы защиты от копирования блокируется следующий функционал:
- Последовательные порты RS485-1 и RS485-2 (модуль `serial.c`) перестают принимать и отправлять данные
- TCP-клиент (модуль `tcp_client.c`) перестает принимать и отправлять данные, но при этом продолжает работать (поддерживает подключение к серверу)
- TCP-сервер (модуль `tcp_server.c`) перестает принимать и отправлять данные, но при этом продолжает работать (принимает входящие подключения)
- Не сохраняются настройки WiFi, Ethernet и портов RS-485 (модуль `settings_manager.c`). Сохранение общих настроек (в т.ч. управление MIO и Vout) продолжает работать штатно

## Проверка статуса системы защиты

Для проверки статуса системы защиты на производстве реализован HTTP GET-запрос:

``` http
GET /wb_status
```

В ответ отправляется JSON со статусом системы защиты. Пример ответа устройства:

``` json
{
	"fw_status":	"ok"
}
```

***Примечание:*** для получения результата необходимо предварительно авторизоваться, т.е. необходимо в GET-запросе передавать валидный ID сессии.

Поле `fw_status` может иметь следующие значения:
- `unknown` - система защиты еще не выполнила все проверки
- `ok`- устройство является валидным и разрешена работа полного функционала
- `fail` - устройство не является валидным, работа основного функционала блокирована
